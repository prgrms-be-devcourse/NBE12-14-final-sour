# 리뷰 규칙

이 레포는 Spring Boot 4 / Java 25, PostgreSQL + Flyway, Redis(Lua 스크립트), Testcontainers를 쓴다.
기여도·순위 같은 실시간 값은 Redis가 원본이고, DB는 배치로 반영되거나 구매 이력 같은 기록을 담는다.
그래서 이 레포에서 가장 비싼 버그는 "Redis와 DB가 어긋나는 것"이다. 리뷰도 그 순서로 본다.

## 리뷰 방식
- 모든 리뷰 코멘트와 PR 요약은 반드시 한국어로 작성한다 (코드, 클래스·메서드 이름, 기술 용어는 원문 그대로 둔다).
- 지적할 때는 세 가지를 같이 쓴다: 무엇이 문제인지, 어떤 입력·순서·상황에서 터지는지(재현 조건), 어떻게 고칠 수 있는지.
- 확실하지 않은 라이브러리·프레임워크 동작은 단정하지 말고 "확인 필요"라고 쓴다.
- 지적은 아래 우선순위로 한다. 위쪽 문제가 있으면 아래쪽 사소한 지적보다 먼저, 더 분명하게 쓴다.
    1. 데이터가 어긋나거나 사라지는 문제 (Redis·DB 불일치, 보상 누락, 유실)
    2. 동시성 문제 (경쟁 조건, 중복 처리)
    3. 보안 문제 (권한 우회, 입력 검증 누락, 민감 정보 노출)
    4. API 계약 변경 (요청·응답·에러 코드가 바뀌어 프론트가 깨지는 것)
    5. 테스트가 동작을 제대로 검증하지 못하거나 환경에 따라 간헐 실패하는 것
    6. 성능 (N+1, 불필요한 쿼리, 긴 트랜잭션)
- 다음은 지적하지 않는다: 코드 포매팅·줄바꿈, 취향에 가까운 이름 바꾸기, 이미 팀 컨벤션을 따르는 코드의 다른 스타일 제안.

## 팀 컨벤션
- 응답은 ApiResponse로 감싼다.
- 비즈니스 오류는 ErrorCode enum에 코드를 추가하고 BusinessException(ErrorCode)으로 던진다. 문자열 메시지만 담은 예외나 일반 RuntimeException을 직접 던지면 지적한다.
- 시각은 OffsetDateTime을 쓰고, 응답은 KST로 내보낸다. LocalDateTime이나 시간대 없는 시각을 쓰면 지적한다.
- Redis 키는 RedisKey enum으로 만든다. 코드에 "user:" 같은 키 문자열을 직접 쓰면 지적한다. RedisKey를 바꾸면 RedisKeyTest의 스냅샷도 같이 바뀌었는지 본다.
- DB 스키마 변경은 새 Flyway 마이그레이션 파일(V다음번호__설명.sql)로만 한다. 이미 있는 마이그레이션 파일을 고치면 지적한다 (이미 적용된 환경에서 체크섬이 깨진다).

## 트랜잭션과 Redis
- Redis 작업은 DB 트랜잭션에 묶이지 않아서, DB가 롤백돼도 되돌아오지 않는다. Redis를 바꾼 뒤 DB 작업이 실패하는 경로에서 Redis를 되돌리는 처리(보상)가 있는지 본다.
- 커밋은 @Transactional 메서드가 끝날 때 일어난다. 서비스 전체에 @Transactional이 걸려 있으면 커밋이 try 블록 밖에서 일어나서, 커밋 실패를 catch로 잡아 보상할 수 없다. 이런 구조를 지적한다.
- 같은 클래스 안에서 this로 @Transactional 메서드를 부르면 프록시를 거치지 않아 트랜잭션이 걸리지 않는다(self-invocation). 이 패턴을 지적한다.
- 트랜잭션 안에서 외부 호출(Redis, 파일 업로드, 외부 API)을 오래 하면 그동안 DB 커넥션을 붙잡는다. 트랜잭션 범위가 필요 이상으로 넓으면 지적한다.
- @TransactionalEventListener(AFTER_COMMIT)는 트랜잭션 밖에서 이벤트를 발행하면 기본적으로 실행되지 않는다. 트랜잭션 구조를 바꾸면서 이벤트 리스너가 조용히 안 불리게 되지 않았는지 본다.
- 보상 처리 자체가 실패할 때 원래 예외를 덮어쓰지 않는지(addSuppressed 등), 어떤 회원·어떤 요청이었는지 로그가 남는지 본다.

## Redis Lua 스크립트
- Lua는 중간에 오류가 나도 이미 실행한 명령을 되돌리지 않는다. 잔액·중복 같은 검사가 모든 쓰기보다 앞에 있는지 본다.
- 되돌릴 수 없는 명령(DEL 등)이 실패할 수 있는 처리(cjson.decode, tonumber 등)보다 앞에 있으면 지적한다.
- 키를 만들 때 TTL이 함께 걸리는지 본다. 만료가 필요한 키에 TTL이 빠지면 영구히 남는다.
- 스크립트가 쓰는 Redis 키는 모두 KEYS로 넘겨야 한다. ARGV나 스크립트 안에서 키 이름을 만들면 지적한다.
- Lua 숫자는 Redis 응답으로 나갈 때 정수로 잘린다. 소수 결과를 그대로 돌려주면 지적한다. 문자열 결과를 숫자로 쓸 때 tonumber가 있는지 본다.
- Lua 표(배열)에 nil이 들어가면 그 자리에서 배열이 끊긴다. 반환 배열에 nil이 들어갈 수 있으면 지적한다.
- 스크립트가 도는 동안 Redis는 다른 요청을 처리하지 않는다. 상한 없는 반복문, 키 전체를 훑는 명령(KEYS 패턴 조회 등)을 지적한다.

## DB와 JPA
- 연관 엔티티를 반복문에서 조회해 쿼리가 N번 나가는 N+1을 지적한다.
- 새 조회 조건이나 정렬이 생기면 그 컬럼에 인덱스가 필요한지 본다.
- "조회 → 값 계산 → 저장" 패턴은 동시 요청에서 마지막 저장이 앞의 저장을 덮어쓴다. 조건부 UPDATE(WHERE 조건으로 원자적 갱신)나 락이 필요한지 본다.
- 엔티티 값이 DB 제약(CHECK, NOT NULL, UNIQUE, FK)을 어길 수 있는 경로가 있는지 본다. 예: expired_at은 created_at보다 뒤여야 한다.

## 동시성
- 같은 데이터를 여러 요청이 동시에 바꿀 때 경쟁 조건이 있는지 본다.
- 클라이언트 재전송·더블 클릭으로 같은 요청이 두 번 와도 한 번만 처리되는지(멱등성) 본다. 특히 재화를 쓰는 요청.

## 보안
- 리소스 소유자는 요청 파라미터가 아니라 토큰의 회원 정보(AuthUser)로 확인하는지 본다. 다른 회원의 ID를 넣어 남의 데이터에 접근할 수 있으면 지적한다.
- 요청 값 검증(@Valid, 범위, 형식)이 빠져 있으면 지적한다.
- 로그에 이메일, 토큰, 비밀번호 같은 민감 정보를 남기면 지적한다. 로그에는 회원 ID 같은 식별자만 남긴다.
- 비밀 값(키, 비밀번호)이 코드나 설정 파일에 그대로 들어가면 지적한다.
- CORS 허용 헤더·origin, SecurityConfig의 인증 경로가 바뀌면 의도한 범위만 열렸는지 본다.

## API 계약
- 요청 헤더·파라미터, 응답 필드, HTTP 상태 코드, 에러 코드가 바뀌면 프론트가 깨질 수 있다. PR 설명에 변경이 적혀 있는지 보고, 없으면 지적한다.

## 테스트
- 테스트 본문은 // given, // when, // then으로 나눈다.
- Mockito는 BDDMockito(given(...).willReturn(...), then(mock).should())를 쓴다. when/verify를 쓰면 지적한다.
- @DisplayName은 "~하면 ~한다" 문장으로 쓴다.
- 통합 테스트는 DB 쿼리(정렬, 페이징, 조건부 UPDATE, 제약 위반)와 Redis(Lua, 키·TTL 동작)만 다룬다. 서비스 로직은 Mockito 단위 테스트, 컨트롤러는 @WebMvcTest로 한다. 통합 테스트로 서비스 분기를 검증하면 지적한다.
- 통합 테스트는 @IntegrationTest를 쓴다. @DirtiesContext는 공유 컨테이너를 닫으므로 쓰면 지적한다.
- 테스트 클래스에 @MockitoBean·@MockitoSpyBean 필드를 따로 두면 그 클래스만 스프링 컨텍스트가 새로 떠서 전체 테스트가 느려진다. 공용 @IntegrationTest에 모을 수 있는지 본다.
- JVM 시각(now())과 DB·Redis가 찍는 시각을 섞어 비교하는 단언은 로컬과 CI에서 결과가 달라질 수 있다. 예: Redis TTL 상한 비교, created_at과의 비교. 절대 시각 비교(PEXPIRETIME)나 충분한 여유를 두는지 본다.
- 단언의 타입이 실제 값과 맞는지 본다. 예: ZSET 점수는 Double이라 700이 아니라 700.0과 비교해야 한다.
- 테스트 데이터가 DB 제약과 실제 사용 방식에 맞는지 본다. 운영 코드가 넘기지 않는 값(예: 만료 시각에 now())을 테스트가 넘기면 지적한다.
- 상태 코드만 확인해서 실제 동작을 검증하지 못하는 테스트를 지적한다. 예: CORS preflight는 일부 헤더만 허용돼도 200이라, Access-Control-Allow-Headers 값을 확인해야 한다.


## 출력 형식
- 코멘트는 GitHub 마크다운으로 작성한다. 줄바꿈은 실제 줄바꿈을 쓰고, `\n` 같은 이스케이프 문자를 글자로 쓰지 않는다.
- 코멘트 하나는 아래 모양으로 짧게 쓴다.
  - 첫 줄: **[분류] 한 줄 요약** (분류: 데이터 불일치, 동시성, 보안, API 계약, 테스트, 성능)
  - **문제**: 2~3문장
  - **재현 조건**: 어떤 입력·순서·부하에서 터지는지 1~2문장
  - **수정 제안**: 1~2문장, 필요하면 코드 블록
- "1. 무엇이 문제인가요?" 같은 질문형 제목을 쓰지 않는다.
- 한 문단은 3문장을 넘기지 않는다.

## 다시 강조
- 요약과 모든 리뷰 코멘트는 한국어로 작성한다.
