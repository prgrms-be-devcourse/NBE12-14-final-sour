# 버전 선정 기준

DB·Redis·언어·프레임워크·라이브러리 버전을 어떤 기준으로 골랐는지 정리한다. "왜 이 버전이냐"는 질문에는 이 문서의 기준과 근거로 답한다.

기준일은 2026-11-27이다. 지원 종료일과 최신 버전은 날이 지나면 바뀌므로, 버전을 바꿀 때는 아래 **출처**를 다시 확인한다.

## 기준

다음 순서로 따진다. 앞의 기준을 통과한 후보끼리만 뒤의 기준으로 비교한다.

1. **운영 환경과 같은가.** 로컬 실행과 통합 테스트는 운영과 같은 버전이어야 테스트 통과를 믿을 수 있다. DB·Redis처럼 운영에 따로 떠 있는 것은 운영 버전이 정답이다.
2. **우리가 쓰는 기능을 지원하는가.** 코드가 쓰는 명령·문법이 그 버전에서 동작하는지 확인한다. 새 버전에만 있는 기능을 쓰면 운영 버전도 함께 올려야 한다.
3. **서로 호환되는가.** 라이브러리는 Spring Boot가 관리하는 버전을 쓴다. Boot가 관리하지 않는 라이브러리는 어떤 Boot 버전을 기준으로 만들어졌는지 확인한다(Maven Central의 POM).
4. **보안 패치를 받는가.** 지원이 끝난 버전은 고르지 않는다. 자료가 많아도 마찬가지다.
5. **지원 기간이 충분하고, 자료가 많은가.** LTS가 있는 기술(Java)은 LTS를 쓴다. 새 기능이 필요 없으면 막 나온 버전보다 사례와 자료가 쌓인 버전을 고른다. 막 나온 버전은 호환성 정보가 적고, AI 도구도 잘 모를 수 있다.

LTS는 모든 기술에 있는 개념이 아니다. PostgreSQL은 모든 주 버전을 약 5년 지원하고, Spring Boot 오픈소스판은 버전마다 지원 종료일이 정해져 있으며, Redis·React에는 LTS 구분이 없다. 그래서 5번은 "LTS인가"가 아니라 "지원 기간이 충분한가"로 본다.

## 선정 결과

### 운영과 맞추는 것 (로컬·통합 테스트)

| 대상 | 버전 | 근거 |
|---|---|---|
| PostgreSQL | `postgres:17` | ① 운영 RDS `sour-postgres`가 **17.9**다(2026-11-27 `aws rds describe-db-instances`로 확인, Terraform `db_engine_version = "17"`). ④⑤ RDS의 PG 17 표준 지원은 2030-02-28까지다. 18의 새 기능(비동기 I/O, `uuidv7` 등)은 쓰지 않는다. 주 버전만 고정해 17.x 패치는 따라간다. |
| Redis | `redis:7.4` | ① 운영 Redis는 Terraform `redis_image = "redis:7.4"`로 띄운다. ② Lua 스크립트와 코드가 쓰는 명령(`ZINCRBY`, `HINCRBY`, `SADD`, `SET … GET`, `PEXPIREAT`, `HTTL` 등)은 7.4에서 모두 동작한다. 마이너 버전에서 동작이 바뀔 수 있어 7.4까지 고정하고 패치만 따라간다. |
| Floci (S3 에뮬레이터) | `floci/floci:2.5.0` | 운영은 실제 S3라 비교 대상이 없다. Docker Hub의 정식 릴리스 중 최신이다(이후는 nightly뿐). `2`, `2.5` 같은 묶음 태그가 없어 정확한 버전으로 고정한다. |

로컬(`compose.yaml`)과 통합 테스트(`TestcontainersConfiguration`)는 같은 태그를 쓴다. `ContainerImageVersionTest`가 두 곳이 같은지, `latest`가 없는지 검사한다.

### 언어·프레임워크

| 대상 | 버전 | 근거 |
|---|---|---|
| Java | 25 (Gradle toolchain, 배포 이미지 `eclipse-temurin:25-jre`) | ④⑤ LTS다. Oracle Premier 지원은 2030년 9월까지다. 다음 LTS인 29는 2027년 9월 예정이다. 빌드와 배포 이미지를 같은 25로 맞춘다. |
| Spring Boot | 4.1.x | ④ 4.1 라인 오픈소스 지원은 2027-07-31까지다. ③⑤ 2026-11-19에 나온 4.2는 아직 쓰지 않는다. Spring Cloud AWS 4.2.x는 Boot 4.0.7을 기준으로 만들어졌고, 4.2와의 호환은 우리 테스트로만 확인할 수 있다. 4.2로 올릴 때는 별도 PR에서 전체 테스트를 돌린다. Spring Boot 3.5는 오픈소스 지원이 2026-06-30에 끝나 고를 수 없다. |

### Spring Boot가 관리하지 않는 백엔드 라이브러리

| 대상 | 버전 | 근거 |
|---|---|---|
| springdoc-openapi | 3.2.0 | ③ 3.2.0은 Boot 4.1.2, 3.2.1은 Boot 4.2.0을 기준으로 만들어졌다(POM의 부모 버전). Boot 4.1을 쓰는 동안은 3.2.0이 맞다. |
| Spring Cloud AWS (BOM) | 4.2.1 | ③ S3 모듈 버전을 BOM 한 곳에서 맞춘다. 4.x는 Boot 4 라인용이다. 4.2.2가 있지만 바뀐 내용을 확인하지 못해 올릴 근거가 없다. |
| jjwt | 0.13.0 + `jjwt-gson` | 최신이다. ③ `jjwt-jackson`은 Jackson 2를 끌어오고 프로젝트는 Jackson 3을 써서 Gson 모듈을 쓴다. |
| testcontainers-floci | 2.9.0 | 이미지 이름만 확인하는 라이브러리라 이미지 태그와 번호가 따로 간다. 2.17.0이 있지만 올릴 근거를 확인하지 못했다. |

PostgreSQL JDBC 드라이버(42.7.x)와 Flyway(12.x)는 Spring Boot BOM이 정한다. 드라이버 번호는 DB 서버 버전과 관계없고, 한 드라이버가 여러 서버 주 버전과 통신한다. 서버 버전에 맞춰 따로 바꾸지 않고, Boot를 올릴 때 함께 올라가게 둔다.

## 사례: 운영과 맞추자 드러난 문제

통합 테스트는 원래 Redis 8.10에서 돌았다. 운영(7.4)에 맞춰 7.4로 바꾸자 `RedisHandler.setHashFieldTtl`이 `ERR unknown command 'HSETEX'`로 실패했다. `HSETEX`는 Redis 8.0에서 생긴 명령이라 7.4에는 없다. 이 메서드는 쓰는 곳이 없어 운영에서 터지지는 않았지만, 누가 쓰기 시작하면 운영에서 바로 실패했을 것이다. 쓰는 곳이 없어 메서드와 테스트를 지웠다.

기준 1(운영과 같은 버전으로 테스트)과 기준 2(쓰는 기능이 그 버전에서 되는가)를 지켜야 하는 이유다.

## 버전을 바꿀 때

- DB·Redis·Floci: `compose.yaml`과 `src/test/.../TestcontainersConfiguration.java`를 한 PR에서 같이 바꾼다. 운영(Terraform `envs/prod`)을 바꾸면 이 둘도 같이 바꾼다.
- 바꾼 뒤 `./gradlew test`와 `./gradlew integrationTest`를 전부 돌린다.
- 로컬 Postgres 주 버전을 바꾸면 기존 컨테이너 데이터를 새 버전에서 열 수 없다. `docker compose down -v`로 지우고 다시 띄운다(로컬 데이터는 사라진다).
- 적용된 Flyway 마이그레이션 파일은 고치지 않는다. `V1__init.sql` 머리말의 "PostgreSQL 16"은 그래서 그대로 둔다(고치면 체크섬 검증이 실패한다).
- 이 문서의 표와 기준일을 함께 고친다.

## 확인하지 못한 것

- 운영 Redis 서버에서 실제 버전(`redis-cli INFO server | grep redis_version`)을 확인하지 않았다. 위 내용은 Terraform 설정 기준이다. 8.x로 나오면 테스트도 그 버전으로 맞춘다.

## 확인 결과 (2026-11-27, `fix/version`)

- `./gradlew test` 통과
- `./gradlew integrationTest`: PostgreSQL 17, Redis 7.4에서 622개 중 621개 통과. 남은 1개(`AttackIntegrationTest`)는 테스트 DB 컨테이너 연결이 끊긴 것(`Connection refused`)이고, 다시 돌려 통과했다.
